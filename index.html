Who this is for

You've built something with Claude, or you want to. You can describe what you want, but you can't read the code that comes back. Some sessions go beautifully. Others go sideways: Claude builds the wrong thing, says it's done when it isn't, or forgets a rule you gave it yesterday.

Almost every one of those failures comes from the same two gaps: Claude was missing something it couldn't see, or it had no way to check its own work. This library closes both gaps. By the end you'll know the names of the pieces, where each one lives, and the exact words that get Claude to build what you meant.

Straight talk

The belief most builders hold, and most need to drop: "more rules make Claude more reliable." Each time something goes wrong, it's natural to add a rule. After a few months the instruction file is hundreds of lines long, some rules contradict each other, and Claude follows all of them a little less. Anthropic's docs say longer instruction files reduce how well Claude follows them. Book 12 shows how to cut a bloated file back down.

What needs a check before launch

You may have heard this way of building called vibe coding. Andrej Karpathy coined the phrase in 2025 for describing what you want to an AI and accepting what it writes without reading it. Simon Willison, the most consistent independent writer on doing this responsibly, keeps the name for exactly that: building without reviewing the result. Once the work has been reviewed and tested and you can explain what it does, he calls it plain software development.

Both ways of working have a place. This library's own rule for telling them apart:

Fine to build on trustAlways gets a check before launch
Personal tools only you useLogins and accounts
Prototypes and experimentsPayments
Small features that nothing else in the app depends onAnything that stores other people's data
API keys and other secrets (the passwords your app uses to reach paid services)
Database access rules (who may read and write what)

Why the right-hand column exists: in a 2025 test by the security company Veracode, covering more than 100 AI models, 45% of the code samples failed security tests. Veracode sells security scanning, and its tasks were designed to expose common weaknesses, so read that figure as a worst case, not an average. It is still a reason not to take the right-hand column on trust.

Straight talk

Erik Schluntz, an Anthropic researcher, argues that unreviewed AI code can be acceptable in the parts of a system nothing else depends on, and that building this way is not for people with no technical grounding. If you can't read code, that warning is about you. This library's answer: you may not be able to review the code, but you can insist on checks that don't need you to read it. A site check that runs on every change (Book 21), a reviewer that never saw the code being written (Book 13), the rules prompt in Book 5, the security check in the Prompt library (Book 18), the security pass in Books 19 and 20, and proof you can see on your own phone. For everything in the right-hand column, those checks are not optional.

What a web app actually is

Most apps people build with Claude are web apps: files that a phone's browser downloads and runs. Once you can name the pieces, you can point Claude at exactly the right one.

Three languages, three jobs

.html

HTML: what is on the screen

The structure: headings, buttons, text, images. Think of it as the nouns. index.html is the page a browser opens first.

.css

CSS: how it looks

Colors, fonts, spacing, layout, animation. In FlashDeck the whole look lives in css/app.css.

.js

JavaScript: what it does

Behavior: what happens on tap, timers, saving progress, 3D scenes, talking to a server. The verbs.

A browser (Chrome, Safari) is the engine that reads these three and draws the app. FlashDeck's index.html is under 50 lines because it hands everything else to css/app.css and the files in js/. TeamDesk's is 15,000 lines because the HTML, CSS and JavaScript are all packed into one file.

Front end and back end

Front end is code that runs on the user's phone, inside the browser. Back end is code that runs on a server you don't hold in your hand. Most beginner apps are front end only, which developers call a static site: a host hands the files to the phone as they are, and the phone does all the work.

TeamDesk needs more. It has an api/ folder of back-end code running on Vercel's servers, because some jobs must never run on a phone:

  • Secret keys. api/reply.js and api/summary.js call the Claude API with a key that costs money per request. If that key were in the front end, anyone could copy it from their browser.
  • Sending to other people. Push notifications and email.
  • Checking secrets. Verifying a team sign-in code.
  • Running on a schedule. A daily job, set up in vercel.json.

Three ways small apps are organized

Corner Gym, TeamDesk

A. One big file

Everything in index.html. Fast to start. Gets harder with every feature: Claude has to search for the right section, and one change can break an unrelated one.

ExamTown

B. Split source, built into one file

You edit small files in src/; a script glues them together. Good when one self-contained file is the deliverable. Adds a build rule to remember.

FlashDeck

C. Small files, no build

One job per file: store.js saves, srs.js schedules reviews, speak.js reads aloud. Claude can change one piece safely and test it alone. Use this for your next app.

Structure is something you request up front, in the spec. FlashDeck is well organized because its spec asked for small files and tests from day one. Adding structure to an 15,000-line file later is a project in itself.

Straight talk

If one of your apps has grown into a single giant file, splitting it should come before the next big feature. Every session pays to search that file, and every edit risks breaking a section nobody was looking at.

The counter-argument: a split delivers nothing visible to users and can introduce bugs. That's real. Do it in small phases (one section per pull request), with the checks run after each.

Prompt for a big single-file app

Protect main with a branch rule

Many builders write "ask before anything that touches main" in their instructions. That's guidance Claude reads, so it's followed nearly every time. Anthropic's best-practices guide says that before you let a scheduled task run without you, you should protect main with a GitHub branch rule the task can't bypass. A branch rule is enforced by GitHub itself.

  1. Open the repo's settingsOn GitHub: your repo, then Settings, then Branches (or Rules, then Rulesets).
  2. Add a rule for mainRequire a pull request before merging, and require your check (for example "Site check") to pass.
  3. Repeat for each live repoStart with the app that has the most real users.

Or ask Claude: "Walk me through adding a branch rule on main for this repo that requires a pull request and a passing site check. Give me exact clicks."

Public repos

Anything ever committed to a public repo stays visible in its history, even after you delete the file. Never commit API keys or passwords; they belong in environment variables (Book 5). One exception surprises people: the web "apiKey" that Firebase creates for you is safe in the front end, as long as it is used only for Firebase. Firebase security comes from its rules file, not from hiding that key. Don't stretch the exception to other keys. Firebase's own page says a key for Gemini (Google's AI) must never be in your code: anyone could copy it and spend your money. That one stays on the server, like every other paid key.

Try it
Prompt for any repo
Show me the last 10 commits on main in plain English: what each one changed for a user, not for a programmer. Then tell me how I would undo the most recent one if it broke something. Also check the whole history for any committed keys or passwords.

Forks, and giving changes back

A fork is how you work on someone else's app without touching theirs. Giving your changes back is a separate step, and with a friend's app it starts with a conversation, not a button.

What a fork is

A fork is your own copy, on GitHub, of a repo someone else owns. GitHub remembers the link between the two. The original is called the upstream. You can change your fork as much as you like; nothing reaches the upstream until its owner accepts it.

WordWhere the copy livesWho owns itUse it for
ForkOn GitHub, under your accountYouWorking on someone else's repo when you can't (or shouldn't) write to it
CloneOn a computerWhoever owns the repo it came fromWorking on files locally. Cloud sessions clone for you.
BranchInside one repoThe repo's ownerA parallel line of work in a repo you can already write to
Example: Pocket Pet

A friend built Pocket Pet and asked for help. You forked it, so your copy lives at you/pocket-pet and publishes to your own GitHub Pages address, separate from their live site. One fork quirk to know: GitHub doesn't run a new fork's workflows (including a Pages deploy) until you switch them on in the fork's Actions tab.

A few weeks later your fork has music, new animations and a dozen fixes. Your friend's copy hasn't changed. The two have drifted apart, and that's the moment this book is about.

Three ways to give changes back

Route A

Pull requests from your fork

You keep working in your fork and send a pull request per feature. The owner reviews each one and merges what they want. Best when they want control over every change.

Route B

They make you a collaborator

The owner adds you to their repo. You work on branches inside it and open pull requests there. One repo, one live site, nothing to sync. Best for ongoing work.

Route C

Your version becomes the new version

If they like everything, they accept your fork's state as a whole, in one large merge or by moving to your repo. Best when the two have grown too far apart to merge piece by piece.

Straight talk

"I'll change it and give it back when I'm done" gets harder every week. A fork that's dozens of features ahead can't be reviewed as one pull request: the owner would have to accept or reject the whole thing. And any changes they make in the meantime will conflict with yours.

Talk to the owner early, before the fork drifts far. Ask which route they want. If it's Route A, keep each pull request small and themed, starting from their latest code. Settle big decisions together too, like renaming the app: it's their app.

The counter-argument: if they're happy for your fork to become the main version (Route C), splitting it up is wasted work. That's exactly why you ask first.

How to ask the owner

A short message works better than a long one. Say what you did, offer the choices, and ask how they want to review. Two drafts to adapt:

Asking which route they want
Hey! I've been working on [app] in my copy on GitHub (my fork). It's live here so you can try it: [your link]

New since your version: [3 or 4 biggest things, in plain words].

How do you want the changes back?
1. I send you small pull requests one feature at a time, and you pick what to keep.
2. You add me as a collaborator on your repo, so I work there directly.
3. My version becomes the new main version.
When a pull request is ready
I sent you a pull request on GitHub: "[title]". It adds [feature] and nothing else. There are before and after screenshots in it, and a "try this" list. If you like it, press "Merge pull request". If not, leave a comment and I'll change it.

What you need on GitHub

From you

  • A GitHub account and a fork. Open the original repo and press Fork.
  • Write access to your own branch. GitHub's docs: to open a pull request in a public repository, you need write access to the head or source branch, which is your fork. For a public repo you don't need the owner's permission to open a pull request, only for it to be merged.
  • Your fork kept in sync. On your fork's page, open Sync fork, then Update branch. If their changes conflict with yours, GitHub prompts you to open a pull request to sort it out.
  • Workflows switched on in the fork, if you want its checks or Pages deploy to run.

From the owner

  • For Route A: nothing in advance. They review and press merge.
  • For Route B: they open their repo's Settings, then Collaborators, and add your username. You accept the invitation from your email or GitHub notifications.
  • For a private repo: they have to give you access before you can fork it at all.
  • Their OK on reuse, in writing. If the repo has no license file, the code stays theirs by default. Being asked to help covers contributing; if your fork ever becomes its own app, get their agreement in a message and add a license.

Things that don't copy to a fork

  • Secrets. Keys stored in the original repo's settings aren't available in your fork, and pull requests from forks don't get them.
  • Settings. GitHub Pages, branch rules and collaborators are set separately for each repo.
  • Issues and discussions. They stay on the original.

Sending a pull request upstream, step by step

GitHub's own steps, in order:

  1. Start from their latest codeSync your fork first, then make a new branch for just this feature. (Claude does this part; see the prompt below.)
  2. Open their repoA yellow banner offers Compare and pull request for your recently pushed branch.
  3. Compare across forksClick compare across forks. Base repository: theirs, branch main. Head repository: your fork, and your feature branch.
  4. Title and descriptionPlain English, written for the owner, with screenshots and a "try this" list.
  5. Allow edits from maintainers (optional)Lets the owner fix small things in your pull request themselves. If your fork contains GitHub Actions workflows, GitHub shows it as Allow edits and access to secrets by maintainers, and its docs warn this also lets them edit the fork's workflows. Between friends that's usually fine; know what it means.
  6. Create pull requestOr choose Draft to get an early opinion before it's finished.

Prepare one feature for the owner

Bring over only the changes that feature needs, nothing else. Environment variables

An environment variable is a named setting stored on the host, outside the code. TeamDesk's ANTHROPIC_API_KEY lives in its Vercel project settings. The code in api/reply.js reads it by name when it runs. The key never appears in the repo, so nobody reading the code can spend your credits.

How to ask for one: "This feature needs a new environment variable. Tell me its exact name, what the value looks like, and the exact clicks to add it in Vercel. Put the name in a code block, one per line."

Changing what's saved

If version 2 of FlashDeck saves progress as {"mastered": [...]} and version 1 saved {"done": [...]}, the new code must read the old shape and convert it. Otherwise every user loses their progress on the next update. Developers call this a data migration.

Say it like this: "This changes the shape of the saved data. Include a migration so existing users keep their progress, and add a test that loads an old save."

Keys for tools Claude uses while it works

Environment variables on the host are for keys your app uses. A different case: a paid tool that Claude uses while building, such as a voice or picture generator for Corner Gym's class videos. In a cloud session there are three tempting places for that key, and all three are wrong:

Tempting placeWhy not
Pasted into the chatIt is now in the conversation for good.
A file in the repoIn a public repo, everyone can read it, and it stays in the history after you delete it (Book 3).
An environment variable on the cloud environmentAnthropic's page: "Anyone who uses the environment can read the values."

The right place is a network secret. On claude.ai/code, open your cloud environment's settings, choose Network secrets, then Add secret. You give it the tool's address (for example api.example.com) and the key. From then on the key is attached to requests to that address after they leave the session, so Claude can use the tool without ever seeing the key. You can't view the value again after saving, so keep your own copy somewhere safe.

  • A cloud session can't reach every site. A new environment starts with limited network access. If Claude reports that a site is blocked, that is the setting working, not a bug. The environment's settings hold the list of sites it may reach.
  • The key still spends money. Set a monthly spending limit on the tool's own website before you add it, and tell Claude the budget: "Ask me before any step that would generate more than five clips."
  • What the tool makes may not be yours to publish. Read its license before the sounds or pictures go into a public repo.

How to ask: "This task needs the [tool] API. Don't ask me to paste a key. Tell me the exact address it calls so I can add a network secret, then try one small request to prove it works."

Security rules

A database like Firestore decides who can read and write each collection using a rules file. Apps built quickly often start with open rules "for testing", or with a switch that keeps things open until someone turns it off. TeamDesk had one: a trial switch that left the database open until the owner locked it. These get forgotten once real people join.

Straight talk

If your app shares data between people, check your rules today, not after launch. Two questions: who can read and write each collection right now, and does the live configuration match the file in your repo? The file is only what you last deployed or pasted.

Open rules are the most common way a quickly built app leaks data, whatever database it uses. In May 2025 a flaw was published under the ID CVE-2025-48757 against Lovable, a tool that builds apps from prompts: apps it generated could go live with database tables that anyone on the internet could read or write. A researcher, Matt Palmer, reported finding 170 such apps among the 1,645 he scanned. Lovable disputes the listing and says each customer is responsible for protecting their own app's data. That dispute is the lesson: the tool that builds your app will not check your rules for you.

The cause there was the access rules of Supabase, another popular database. Its version of a rules file is called Row Level Security: a switch on each table, plus written policies that say who may see which rows. Supabase's docs say that once the switch is on, no data can be reached with the app's public key until you write a policy. Firestore's rules file does the same job for TeamDesk. Whichever database you use, the two questions above are the check. Book 6 shows an open rule beside a safe one, and how a rule goes live.

Rules: an open one beside a safe one

Rules are the only thing standing between the internet and your database. The app's code doesn't count: anyone can talk to the database directly, without your app, using the configuration from section 3. Here are three rules. Learn to tell them apart by sight, because you will be the one checking.

Open. Never publish this
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /{document=**} {
      allow read, write: if true;
    }
  }
}

if true means "always". Firebase's page on insecure rules: "anyone who guesses your project ID can steal, modify, or delete the data."

Looks safe, is not
    match /{document=**} {
      allow read, write: if request.auth != null;
    }

request.auth != null means "is signed in". Firebase's words: "Any logged-in user has read and write access to your entire database." Every TeamDesk user could read every other team's messages. With anonymous sign-in on, "logged-in" means everyone.

Safe: each user reaches only their own data
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{uid} {
      allow read, write: if request.auth != null && request.auth.uid == uid;
    }
  }
}

The added part, request.auth.uid == uid, means "and the data is filed under this user's own id". Anything not named in the file is refused. Shared data, like a team's messages, needs a longer rule that checks team membership. Ask Claude for it, then ask for the plain-English table in the prompt below.

Why people keep seeing the old version

A phone almost never loads your app fresh from the host. To be fast, and to work with poor signal, something along the way keeps a copy and hands that over instead. There are three such places. When someone sees an old version, the first job is working out which one it is.

Where the old copy sitsWhich apps have itHow long it lasts
1. The host hasn't switched yetEvery appMinutes. GitHub: "It can take up to 10 minutes for changes to your site to publish".
2. The browser's saved copy, or a page that was never closedEvery appUntil the page is loaded again. An app left open on a Home Screen can sit on last week's version for days.
3. The offline worker's saved copyOnly apps that were given an offline worker (a file usually named sw.js)Until the worker is told there is a new version, and then until it is allowed to switch. This is the one that lasts.

The browser's saved copy is called its cache. MDN, the web's reference manual, describes it in one line: it "stores a response associated with a request and reuses the stored response for subsequent requests." A copy that is past its date is called stale.

Straight talk

One case is left: the app that is never closed. Someone added Corner Gym's website to their Home Screen in March and has switched back to it ever since. The page was loaded once and has had no reason to load again. They are still looking at March's class videos.

The fix is small. Each time the app comes back to the front of the phone, it asks the host one question: has the page changed since I loaded it? If yes, it loads the new one. Apps with an offline worker: three update styles

An offline worker is a small script that keeps a copy of the app on the phone so it opens with no signal. Developers call it a service worker. Book 21 leaves it out on purpose. Add one only when people need the app without signal, because from that day updates are something you plan.

Here is what the browser does if nobody plans anything. When the app is opened, the browser checks whether the worker file has changed. If it has, the new version is downloaded in the background while the person keeps using the old one. Then it waits. MDN: the new version "is only activated when there are no longer any pages loaded that are still using the old service worker." So the person sees your fix on the open after the next one, and only if the app was fully closed in between. People rarely close an app fully.

Two things follow. The browser only notices a new version if the worker file itself changed, which is why other books say to bump CACHE_VERSION in sw.js: changing that one line is the signal. And someone has to decide when the waiting ends. There are three sensible answers.

  • A robot. GitHub Actions can run a job "when someone pushes to main". Ask Claude for one that sets the version from the date and time of each merge. Then it can't be forgotten, because no person does it.

What never updates by itself

Two things don't arrive with the next merge, whatever style you chose.

The name and icon on the Home Screen

The name and icon come from the manifest (Book 21), and the phone reads them when the app is installed.

PhoneWhat the official pages say
iPhone (Safari)Google's web.dev: "the only way to get the new manifest metadata is to re-install the app from the browser."
Android (Chrome)Chrome looks for manifest changes at most once every 24 hours. "In most cases, changes should be reflected within a day or two" of the app being opened, and only once the phone is plugged in, on Wi-Fi, and the app is closed.

So choose the name and the icon as if they were permanent. On iPhones they are, unless every user removes the app and adds it again. Before anyone does that, have them save a backup file (Book 21). Don't count on saved progress surviving a removal.

Saved data in the old shape

The new code arrives on a phone that still holds data saved by the old code. If the new version expects a different shape, people's progress looks empty or the app breaks on open. This is the migration from Book 5, and it matters more with slow update styles: under style A, phones on three different versions can be in use in the same week. Add to any request that changes what is saved: "Assume phones are updating from any earlier version, not only the last one."

If the app is in a store wrapper

None of your apps needs this today. It is here so the word "update" doesn't surprise you later. A wrapper is a thin store app whose screen shows your web app. Capacitor is a common tool for making one. A wrapped app has two parts, and they update differently.

PartWhat it isHow a change reaches phones

Capacitor's page puts the line here: live updates work "as long as those changes do not require binary updates (aka compiled native functionality)." In plain words: as long as the native part is untouched.

The stores' own rules, in their words:

  • Apple, guideline 2.5.2: apps may not "download, install, or execute code which introduces or changes features or functionality of the app". Guideline 4.2 asks for "features, content, and UI that elevate it beyond a repackaged website".
  • Google Play: an app "may not modify, replace, or update itself using any method other than Google Play's update mechanism." A web view is the screen inside a wrapper that shows your web app, so that exception describes the web part.
Straight talk

These rules leave room for argument. This library's advice is the cautious reading, not a rule either store states: send fixes, wording and content as a live update, and send a new feature through review even when it is only web code. Asking Claude for it

The prompts in sections 2 and 3 set the update style. Three habits make it checkable.

A version people can read out

An update can only be tested on a phone that already has the old version. A fresh install always gets the newest files and proves nothing.

  1. Install the current version on two phonesOr one phone and one computer. Open the app on both and note the version number.
  2. Merge a small visible changeA word on the home screen is enough. Wait ten minutes for the host.
  3. Phone one: use it the way people doSwitch away and back. Don't close anything. Write down how many times you had to come back before the new version showed.

Why thin wrappers get rejected

Both stores have a rule aimed at exactly what a beginner would submit: a website in a wrapper.

  • Apple, guideline 4.2: "Your app should include features, content, and UI that elevate it beyond a repackaged website." And: "If your app is not particularly useful, unique, or "app-like," it doesn't belong on the App Store." Apple's review page lists "Web clippings, content aggregators, or a collection of links" and "Not enough lasting value" among the common problems.
  • Google: "We do not allow apps that only have limited functionality and content." Its examples include "Apps that are static without app-specific functionalities, for example, text only or PDF file apps". Its spam policy also bans apps that "provide a webview of a website without permission from the website owner" (a webview is the screen inside a wrapper that shows a site). You own your site, so that one is not about you, but it shows how closely wrapped websites are watched.

Apple says it reviews "at least 50% of submissions in less than 24 hours and 90% in less than 48 hours." The first wait is short. Apple gives no figure for being turned down and trying again; expect that to take far longer.

What "more than a website" tends to mean

Neither store publishes a checklist, so this part is this library's reading of those rules, not a promise of approval:

  • It does something, and keeps doing it. FlashDeck schedules your reviews and remembers your progress. A page of gym opening hours would likely not pass.
  • It behaves like an app. No browser bars, no links that throw the person out to a website, nothing that says "open in browser", no dead buttons, no "coming soon".
  • It opens with no signal and says something sensible when it can't load.
  • It is finished. Apple's own list of common problems starts with "Crashes and bugs", "Broken links", "Placeholder content" and "Incomplete information".
The risky shortcut: wrap it as it is and see what happens

The tools make wrapping quick, so it is tempting to submit today's website and let the reviewer say what is missing.

What it costs: the fee is paid before the first review. Each rejection means building and submitting again. And an app that needs no signal means an offline worker, which Book 7 says to add only with an update plan.

How Claude Code works

A chat writes text for you to copy. Claude Code works inside your repo: it reads files, runs commands, edits, checks its own work and commits. Knowing how that loop runs explains most of the advice in this course.

The loop

  1. Gather contextReads CLAUDE.md and rules, then the files the task needs, and searches the repo.
  2. ActEdits files, runs commands, installs things it's allowed to.
  3. CheckRuns whatever tells it pass or fail: your site-check, tests, a screenshot. If there's no check, "looks done" is all it has.
  4. Repeat or reportFixes what failed, or stops and tells you.

Anthropic's guide puts it bluntly: when Claude has nothing to run that says whether the work is done, you become the test suite. That's why a rule like "never say done without running it" is worth having.

The context window

Claude's working memory for a session is called the context window. Everything in it is re-read on every turn: your messages, its replies, every file it opened, every command output, and every instruction file loaded at the start. Two consequences:

  • Long sessions get summarized. When the window fills, the conversation is compacted into a summary. Anthropic notes that instructions given only in conversation are lost when that happens. A decision you want kept goes into a file.

  • HTML comments (<!-- note -->) are stripped before loading, so you can leave notes for yourself that cost Claude nothing.

What belongs in it

Anthropic's guide lists four kinds of content:

1

How to check work

The exact commands for tests, type checks and lint, and how to run one test file. "If your repo already has one of these, the single most useful line in your CLAUDE.md is the command that runs it."

2

Where the code misleads

An old pattern new code shouldn't copy, a folder that looks unused but isn't. For ExamTown: "index.html is built from src/."

3

Decisions not in the repo

Why things are the way they are, how deploys work. For example: "Budget is $0", "never store customers' personal information".

4

Anything corrected twice

If you've had to say it twice, write it down once.

What to leave out

  • What Claude can find by reading the code. Anthropic lists "describe your architecture and file layout in CLAUDE.md" among advice you can stop following, because Claude reads the repo itself.
  • Generic good practice. "Write clean code" changes nothing.
  • Long procedures. Those go in a skill, which loads only when needed.
  • Rules with zero exceptions. Those go in a hook or deny rule.
  • Personal preferences. Those go in CLAUDE.local.md.
Anthropic's two-question test

Before writing anything down for Claude: (1) Could it find this by reading the code? (2) Would it actually go and look? If both answers are yes, leave it out.

Size and wording

  • Under 200 lines per file. Longer files consume more context and reduce adherence.
  • Specific and checkable. "Run node .github/site-check.cjs index.html before asking me to approve" beats "test your changes".
  • Markdown headers and bullets, so it scans.
  • No contradictions. If two rules disagree, Claude may pick one arbitrarily.
  • No IMPORTANT or ALL CAPS. Anthropic now says current models follow a plain line, and piling on emphasis makes Claude over-apply the rule. If a line keeps getting missed, either the file is too long or the line belongs in a hook.
  • Give the reason. Anthropic's prompting guide shows that "never use ellipses" works worse than explaining that a text-to-speech engine will read the response and can't pronounce them. A reason lets Claude handle cases the rule didn't foresee.
  • Say what to do, not only what not to do. "Use the colors in DESIGN.md" works better than "don't invent colors".

Signs of a healthy setup

Six fixes, ranked

1. Shrink what loads every session

TeamDesk's CLAUDE.md is only 64 lines, but its first line imports a 470-line AGENTS.md. Claude reads 534 lines before every task, including a one-word copy fix. AGENTS.md got long because it holds procedures (how a session runs, branching, handoffs) and topic rules (database, server functions, chat) that only matter some of the time.

  • Keep in the always-loaded files only what's true for every task: who it's for, what it must never do, the check commands, the branch rule. Aim for 120 to 150 lines.
  • Move topic rules to .claude/rules/ with paths: (for example firestore.rules; api/**).
  • Move procedures to skills you start yourself: /handoff, /phase.
A catch with AGENTS.md

Other AI tools don't read .claude/rules/. If they still need a moved rule, keep a one-line pointer in AGENTS.md ("Database rules: see docs/database.md") instead of the whole text.

Prompt (plan mode)
Anthropic recommends keeping always-loaded instructions under 200 lines. Count what loads every session here, including imports. Then propose a split: what stays (true for every task), what moves to .claude/rules/ files with paths: (name the paths), what becomes a skill I start myself, and what can be deleted because you could read it from the code. Show the new line count. Plan only, no edits.

2. Turn "never" lines into enforcement

These lines are each followed almost always, and "almost" isn't good enough for them:

Line in CLAUDE.mdMove it to
"index.html is built. Never edit it by hand."A PreToolUse hook that blocks edits to it (Starter kit, item D)
"Never commit secrets."Deny rules on reading .env files
"Never force push."A deny rule on git push --force, plus a GitHub branch rule on main, which is the lock that can't be worded around
"Ask before anything that touches main."A GitHub branch rule (Book 3), plus an ask rule on pushing to main

Keep a short version of the line in CLAUDE.md too, so Claude knows the reason and doesn't waste a turn hitting the wall.

3. Delete "this file wins" lines; fix the conflict instead

Builders often write "where this file differs, this file wins". Anthropic's docs say instruction files are added together, not overridden, and that conflicting rules may be resolved arbitrarily. A "wins" line is a request, not a mechanism. When two files disagree, change one of them.

4. Stop copying shared rules by hand

Keeping the same short rules file in every repo is the right call for cloud sessions, which can't see your computer's personal folder. The risk is drift: change it in one repo and the others are stale. Keep a master copy in one place (a repo of your own templates) and ask Claude to sync it when it changes.

Prompt
Compare .claude/rules/[shared file].md across these repos: [list]. List any differences. Then make the version in [template repo] the master and give me a one-line prompt I can reuse to copy it into every repo.

5. Replace "read all of this first" with "read this when"

Many files open with "Read first: SPEC.md, docs/ARCHITECTURE.md, DESIGN.md". For a small repo, Claude reads the code faster than three documents about it. Keep an architecture map only where searching is expensive (like an 15,000-line file). Elsewhere: "Read SPEC.md before a new feature; read DESIGN.md before a UI change."

6. Trim anything near 200 before it passes

At 160 lines, Pocket Pet's file is close. It also carries rules written for its original owner's workflow. In a fork you're changing for someone else, decide whose rules apply and cut the rest.

Straight talk

Rules pile up because each one is added after a mistake, and nobody deletes the old ones. A good habit: every rule you add should replace or delete one. Run /doctor prompt-audit once a month in each active repo. If a line is about a problem that hasn't happened in a month, try deleting it and see if anything breaks.

C. Hard limits: permissions

Deny rules hold in every mode, including auto. Ask rules make Claude stop and ask you. After adding, type /permissions in a session to confirm they loaded.

      "Bash(git push -f *)"

      "Bash(git push origin main*)",

    ]

D. A hook that protects a built file (for apps like ExamTown)

A PreToolUse hook runs before Claude edits a file. If the script exits with code 2, the edit is blocked and the message goes back to Claude. Anthropic's tip: you don't have to write hooks yourself; asking "write a hook that blocks edits to X" works, and /hooks shows the result.

.claude/hooks/protect-built.cjs
// Blocks direct edits to the built index.html.
const path = require("path");
let raw = "";
process.stdin.on("data", c => raw += c);
process.stdin.on("end", () => {
  let file = "";
  try { file = JSON.parse(raw).tool_input.file_path || ""; } catch (e) {}
  const root = process.env.CLAUDE_PROJECT_DIR || process.cwd();
  const rel = path.relative(root, path.resolve(root, file)).split(path.sep).join("/");
  if (rel === "index.html") {
    console.error("index.html is built from src/. Edit src/ and run python3 tools/build.py instead.");
    process.exit(2);
  }
  process.exit(0);
});
Add to .claude/settings.json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "node .claude/hooks/protect-built.cjs" }
        ]
      }
    ]
  }
}

Its limit: it watches Claude's Edit and Write tools. A shell command that rewrites the file wouldn't be caught. That's fine for a guard rail; the build itself is the real protection.

The anatomy of a great request

Anthropic's prompting guide suggests treating Claude like a capable new employee who lacks your context. The skill isn't fancy wording. It's handing over what Claude can't see.

Anthropic's colleague test

The prompting guide offers a simple test: show your request to a colleague with minimal context. If they'd be confused, Claude will be too. Claude can read your code. It can't read your mind, your phone, your friend's feedback or the meeting where you decided something.

The five parts

  1. GoalWhat you want and who it's for. "So students can practice timed exams on the train."
  2. WhereThe app, screen, file or URL. "The Drill screen in FlashDeck", "api/summary.js", a screenshot.
  3. ContextWhat Claude can't see: what users said, what you tried, why you want it, what you've decided before.
  4. ConstraintsWhat must stay true. "No new libraries", "$0 budget", "keep DESIGN.md colors", "don't touch firestore.rules".
  5. Done when, plus proofHow you'll both know it's finished, and what you want to see. "Done when 4 answer buttons fit at 390px without scrolling. Send a screenshot."
The template
Goal: [what, and who it's for]
Where: [app, screen, file, or attach a screenshot]
Context: [what you know that isn't in the code: feedback, why, past decisions]
Constraints: [what must not change, budget, libraries, data]
Done when: [a check anyone could verify]
Proof: [screenshots at phone width / a "try this" list / test output]

You won't fill all six every time. A small change might be two lines. But when a result disappoints, the missing part is almost always one of these.

The server decides

Everything in the front end is sent to the visitor's phone (Book 1), and anything on their phone they can read and change. So a button that only shows for the owner, a page with no link to it, or a line of JavaScript that checks "is this the owner?" stops nobody who wants in. The checklist calls this "enforce permissions on the server side". OWASP, the group that writes the standard security guides, puts it bluntly: "Developers must never rely on client-side access control checks."

The risky shortcut: a hidden admin page

TeamDesk's owner has a page at /admin.html that deletes messages and removes people from the team. Nothing links to it, and the page checks the owner's email before it shows the buttons.

What it costs: the check runs on the visitor's phone, so anyone can skip it. If the database rule lets any team member delete messages, the admin page was never the lock: a member can delete everything without ever opening it.

How to close it: put the check where the visitor can't touch it, in the database rules or in server code. Firebase does this with a custom claim, a label such as "admin" attached to one account. Firebase's page says claims should only be set "from a privileged server environment by the Firebase Admin SDK", never from the app itself. A rule then reads the label: allow write: if request.auth.token.admin == true;

Lock the actions, not the page

What matters is what the admin page does: delete, change someone's role, see everyone's data, export a list. Each of those actions needs its own check, every time. OWASP: "Validating permissions correctly on just the majority of requests is insufficient." And start from no: OWASP's rule is that an app "should be configured to deny access by default", then allow each thing on purpose. Firebase rules already work that way; anything not named in the file is refused.

How to ask: "List every admin action in this app (anything only the owner should do). For each one, show me where the server or the database rules refuse it for everyone else. If the only check is in the front end, say so."

Row Level Security, and where it's "appropriate"

Book 5 introduced Supabase's version of rules, Row Level Security. Supabase's own page says: "Enable RLS on every table in an exposed schema." In plain words: every table the app can reach with its public key gets the switch on. Then each table gets a written policy. Supabase's example lets each person see only their own profile, using auth.uid() = user_id, the same idea as Firebase's request.auth.uid == uid.

"Where appropriate" in the checklist does not mean "on some tables". A table of public class times can have a policy that lets everyone read it, but the switch is still on, so nobody can write to it. Supabase's storage follows the same idea: "By default Storage does not allow any uploads to buckets without RLS policies."

The risky shortcut: the secret key in the browser

Supabase gives you two kinds of key. The public one is meant for the app. The secret one skips every policy; Supabase's page says to use it "for administrative tasks that need to bypass RLS" and to "Never use a secret key in the browser or expose it to customers."

What it costs: one key in the front end and every table is open to anyone who opens the browser's developer tools.

How to close it: change the secret key in the Supabase dashboard, keep the new one in a Vercel environment variable (Book 5), and use it only in server code that checks who is asking.

The front door of your server code

Every file in api/ (Book 6) is an address anyone on the internet can call, with or without your app. The checklist says "secure your API endpoints". That comes down to four questions per address:

  1. Who is calling?A signed-in person, checked on the server. The server verifies the login that comes with the request; it never trusts a name or id the app sends.
  2. Are they allowed?Their own data only, or an admin action from an admin (the first two sections).
  3. How often?A limit per person or per address, so a script can't call it a thousand times.
  4. What did they send?Checked on the server before it's used. Book 20, section 2.

Which actions need a limit

"Rate limit sensitive requests" means capping how often one person or one address can do something. The actions that need it are the ones that cost money, send messages or guess passwords:

  • Anything that calls a paid AI. TeamDesk's "draft a reply" calls the Claude API and pays per request. Without a limit, one script runs up your bill overnight.
  • Sending email or texts. Sign-in links, invitations, password resets. Without a limit, your app becomes someone's spam cannon, and the email service may block you.
  • Sign-in and sign-up. Firebase already limits these for you (Book 6 lists 100 new accounts an hour from one address). Code you write yourself has no limit until you add one.

Two ways to add one. Vercel's firewall has rate limiting "on all plans"; the free plan gets one rate limiting rule. Or ask Claude to count in the database: "20 drafts a day per person" is simple, works on any plan, and is easy to check.

How to ask: "For every file in api/: who can call it, what it checks before acting, and how often one person can call it. Add a limit to anything that costs money or sends a message, and tell me the number you picked and why."

Checked in November 2026 against Vercel's WAF rate limiting page and Firebase's Authentication limits.

Logins: borrow one, never build one

The checklist says "hash passwords securely". For apps built from this library the better rule is: never hold a password at all. Firebase Authentication and Supabase Auth store passwords, send reset emails and slow down guessing for you. Your app never sees a password, so it can never leak one.

The risky shortcut: a password column

Ask for "a login" without saying how, and Claude may build its own: a users table with an email column and a password column.

What it costs: one leak exposes every password, and people reuse passwords, so it exposes their email and bank too.

How to close it: say "Use Firebase Authentication (or Supabase Auth). Never store a password in our database." If something truly must store one, OWASP's rules apply: "Passwords should never be stored in plain text", and they must be scrambled with a slow, one-way method (a hash) "such as Argon2id, bcrypt, or PBKDF2". Fast ones like SHA-256 "are not suitable". If Claude proposes anything else, stop it.

Verify email addresses

With email-and-password sign-in, anyone can type anyone's address. Until the address is verified, you don't know the person owns it. That matters as soon as the app emails people, invites them to a team (TeamDesk does), or treats the address as proof of who they are.

  • Firebase: the app sends a verification email (Firebase's function is sendEmailVerification), and the rules can refuse unverified accounts by checking request.auth.token.email_verified. Firebase's own security checklist recommends rules that require a verified email.
  • Already proven: the email link sign-in from Book 6 proves the address by itself, because the person had to open the email to get in.

Where the login is kept on the phone

After someone signs in, the phone keeps a token, a digital pass, so they stay signed in. The checklist says "keep auth tokens out of insecure browser storage". This is the one item where the experts and the tools you use disagree, so here are both sides.

The case for moving the tokenThe case for leaving the default
OWASP: "Do not store session identifiers in local storage as the data is always accessible by JavaScript." If a stranger gets a script onto your page (cross-site scripting, Book 20), that script can read the pass and use it from anywhere. Moving to cookies needs server code that manages sessions, which is more to get wrong. And a script on your page can still act as the user while the page is open, cookie or not.

Whatever you pick, some things never go in browser storage: passwords, your own API keys, Supabase's secret key, anything other than the login library's own pass.

How to ask: "List everything this app saves in the browser (localStorage, sessionStorage, cookies, IndexedDB): each name, what's in it, and who could use it if they copied it. Flag anything that's a password, a key or someone else's data."

Everything typed in is suspect

A form that says "name, 50 letters at most" protects nothing on its own. Anyone can send your server or your database whatever they like without using the form. OWASP: "Validate on the server even when the browser checks the same fields." The form's check is for the honest user, to show a mistake right away. The server's check, or the database rule's, is the one that counts.

  • Validate means checking the input is what you expect: the right type, a sensible length, one of a fixed list of choices. Refuse everything else.
  • Sanitize means making it harmless before it's used or shown. The two dangers below are why.

Cross-site scripting

If a person's text is put on the page as code instead of as text, a "name" that contains a script runs in the browser of everyone who sees it. That is cross-site scripting (often written XSS). The script runs as if it were your app: it can read what Book 19, section 5 said is kept in the browser, and act as the person viewing. TeamDesk shows messages from team members; one poisoned message would run on every teammate's screen.

The fix is a habit, not a tool: show people's text as text. OWASP names the two ways: avoid "unsafe sinks like innerHTML, and instead use textContent". Tools like React show text safely by default, except through what OWASP calls "escape hatches", such as React's dangerouslySetInnerHTML used "without sanitizing the HTML". If the app must allow formatting (bold, links), ask Claude for a well-known sanitizing library, not a homemade one.

Parameterized queries

The same danger, aimed at the database. It only applies when server code writes database commands as text, as it can with Supabase's underlying database. If a person's text is glued into the command, they can rewrite the command; that is an injection. OWASP's fix is "parameterized queries": the command and the person's text travel separately, so the text can never become part of the command. Firestore, and Supabase's normal library calls, do this for you. Hand-written database commands are where it goes wrong.

How to ask: "For every place this app takes input from a person (forms, addresses, uploads): is it checked on the server, and how? Is any of it ever put on a page as HTML, or into a database command as text? Show me each place and the fix."

Uploads, and messages from other services

Corner Gym lets members upload a profile photo. An upload is input too, and a file can be much more dangerous than a name. OWASP's file upload rules, in plain words:

OWASP's ruleWhat it means for you
"Only allow authorized users to upload files"Signed-in members only, into their own folder (Book 19, section 2).
"List allowed extensions"Photos only: say which kinds (jpg, png, webp) and refuse the rest.
"don't trust the Content-Type header as it can be spoofed"A file's label can lie. The check looks at the file, not just its name or label.
"Set a file size limit"Pick a number. Firebase's own example limits uploads to images under 5 MB.

Firebase's storage rules can enforce the size and the kind on their own, so the check holds even if someone skips your app: request.resource.size < 5 * 1024 * 1024 and request.resource.contentType.matches('image/.*').

Webhooks: messages that say "paid"

When Corner Gym sells a class pack, the payment service tells the app it was paid by calling an address on the app's server, say /api/paid. That call is a webhook. Anyone can call the same address and say "paid". Stripe's page: "Without verification, an attacker could send fake webhook events to your endpoint to trigger actions like fulfilling orders, granting account access, or modifying records."

The fix is the signature. Stripe "signs every webhook event" with a secret that only Stripe and your server know (it starts with whsec_), and the function refuses any message whose signature doesn't match. Two details Claude gets wrong often: the check needs "the raw body of the request", exactly as it arrived, and Stripe's own libraries refuse messages more than 5 minutes old, so an old message can't be replayed. Other payment and messaging services sign their webhooks in a similar way; ask Claude to read that service's own page.

How to ask: "Read [service]'s current page on verifying webhooks. Make /api/[name] refuse any message without a valid signature, using their official library and the raw request body. Keep the signing secret in an environment variable. Make it safe if the same message arrives twice. Show me the line that refuses a bad signature."

Quiet leaks: logs, debug mode and headers

Keep sensitive data out of your logs

Logs are the notes your server code writes while it runs (Book 6 shows where to read them on Vercel). While fixing a bug, Claude often writes "log everything the request contained", then leaves it in. OWASP's list of what "should usually not be recorded directly in the logs" includes "Access tokens", "Authentication passwords", "Encryption keys and other primary secrets", payment card data and sensitive personal data. Anyone who can read the logs then has all of it.

Turn off debug mode in production

Many tools have a debug mode that shows detailed errors, sometimes with settings and code, to help while building. Django's docs: "Never deploy a site into production with DEBUG turned on." Flask's are worse news: its debugger "allows executing arbitrary Python code from the browser." Static apps have their own version: a leftover test switch such as ?admin=1, a test login, or a page that prints everything saved.

Add security headers

Headers are short instructions the host sends with every page, telling the browser to be stricter. The most useful is the Content Security Policy, a list of which scripts may run; OWASP calls it a defense against cross-site scripting, and also says it "should not be relied upon as the only defensive mechanism". Others stop your app being shown inside someone else's page, or force a secure connection.

  • On Vercel: headers go in vercel.json; Vercel's page shows how. Vercel's production checklist asks for "a Content Security Policy (CSP) and proper security headers".
  • On GitHub Pages: its documentation offers no way to add your own headers. The fallback is a Content Security Policy in a <meta> tag at the top of the page. MDN says that "does not support all CSP features": OWASP's page notes it still allows "full XSS defenses" but not "framing protections", so stopping another site from showing yours inside its page needs a host with headers.

A Content Security Policy that's too strict breaks the app (fonts, Firebase, anything loaded from elsewhere). Have Claude add it on a preview, open every screen, and check the browser's console for blocked items before it goes live.

Old parts: packages and endpoints

A dependency (or package) is code other people wrote that your app uses, listed in package.json. People find holes in popular packages all the time, and your app has the hole until you update.

  • Dependabot alerts. GitHub's tool that "help you find and fix vulnerable dependencies". Turn it on in the repo: Settings, then under "Security and quality" choose Advanced Security, then Enable next to Dependabot alerts.
  • Dependabot security updates. GitHub's words: "automated pull requests that help you update dependencies with known vulnerabilities." Treat each one like any pull request: the site check must pass, and you look at the preview before merging.
  • npm audit. The command that asks for "a report of known vulnerabilities" in your packages. Claude can run it in a session and explain the results in plain words.

Remove what nothing uses

Every package is more code that can have a hole, and every file in api/ is another door. The worst are leftovers: /api/test, /api/seed that fills the database with sample data, an old version of a function nobody calls. Remove them in a pull request of their own, so if something breaks, you know which removal did it.

How to ask: "List packages in package.json that no code uses, and files in api/ that the app never calls. For each, say what it was for and whether removing it is safe. Remove them in a separate pull request, then run the site check."

3. Each user can reach only their own data, including lists and searches.
4. Row Level Security (or Firestore rules) covers every table or collection.
5. Database and file storage rules are as closed as they can be.
6. Every file in api/ checks who is calling and what they may do.
7. Sign-in, password reset, messages and paid AI calls have rate limits.
8. Email addresses are verified before they're trusted.
9. No password is stored anywhere but the login service.
10. Nothing in browser storage is a password, a key or someone else's data.

Secrets
11. Keys are read only by server code.
12. No environment variable with a public prefix (VITE_, NEXT_PUBLIC_) holds a secret.
13. .env is in .gitignore and was never committed.
14. The whole Git history holds no key or password (the Firebase configuration and Supabase's public key are allowed).
15. The host serves no file a visitor shouldn't see.
16. Logs never record passwords, tokens, keys or personal data.

What comes in
17. Every input is checked on the server, not just in the form.
18. No person's text is ever put on a page as HTML.
19. No database command is built by joining text.
20. Uploads are limited by kind, size and who may upload, and renamed.
21. Every webhook checks its signature.

Before deploy
22. Security headers are set (or, on GitHub Pages, a Content Security Policy meta tag).
23. No debug mode, test switch or test login is on in production.
24. No package has a known vulnerability (run npm audit if there is a package.json).
25. No unused package or api/ file is left.
26. List what you could not check and the exact screens I should open.

Checks only you can do

  1. Live rules match the filesFirebase console, the Rules tab for the database and for Storage. Or Supabase's Security Advisor, which its production checklist says to run "to find issues in your database at any time".
  2. Keys are secretsVercel, Environment Variables: every key has the type Secret. Vercel's page: "Secret values are write-only after saving."
  3. GitHub is watchingThe repo's Security and quality tab: no open secret scanning or Dependabot alerts.
  4. The two-account testFrom the end of Book 19.
  5. Any leaked key is changedOn the service's own website, not just removed from the code.
Straight talk

A table full of "pass" feels like safety. It isn't proof. Claude checking code it may have written itself misses things, and Anthropic's support page says its own security review should "complement, not replace" other checks and human review. Fix in this order: leaked keys first (change them today), then who can reach whose data, then the rest. And as Book 6 says, none of this makes an app ready for health records, payments or children's data. Those have laws attached; pay a person who does this for a living before launch.

Put it online with GitHub Pages

If the app is plain files (HTML, CSS, JavaScript) with no server code of its own, GitHub can host it for free. You turn it on once, by hand, in the repo's settings. Claude can't press these buttons for you.

  1. Open the settingIn the repo on GitHub: Settings, then Pages in the side list.
  2. Pick the sourceUnder "Build and deployment", set Source to Deploy from a branch. Choose the branch main and the folder / (root). Press Save.
  3. Find the linkCome back to the same screen after a few minutes and press Visit site. The address has this shape: https://your-name.github.io/your-repo/. That is the link you send people.
  4. Know the delayGitHub says a change can take up to 10 minutes to show after it reaches main. If the old version is still there, wait before asking Claude to "fix" it.

Three things to know before you rely on it:

  • From now on, merging to main is publishing. There is no preview and no "are you sure". This is why the steps above put a check and a branch rule in place first.
  • On the free plan the repo must be public. Everyone can read every file in it, so it can never hold a key or a password (Book 3).
  • The app lives in a subfolder (/your-repo/). A link inside the app that starts with / works on your computer and breaks on the live site. Tell Claude once: "This site is served from a subfolder on GitHub Pages. Never start a link with a slash."

Book 5 has what Pages may not be used for (a shop, anything taking passwords or card numbers) and when to pick Vercel instead.

Put it on a phone's Home Screen

A web app can sit on the Home Screen with its own icon and open without the browser's bars, like an app from a store. No store, no fee, no review. People do it themselves in two taps, but only if you tell them how.

PhoneWhat the person does
iPhone (Safari)Open the link, tap the Share button, then Add to Home Screen.
Android (Chrome)Open the link, tap the three dots beside the address, then the install choice. Chrome's wording changes between versions ("Install" or "Add to Home screen").

Why it matters more on iPhone. Safari can erase what a site saved on the phone after seven days of browsing without a visit to that site. For a study app that means a week away can wipe someone's progress. The makers of Safari say an app added to the Home Screen is counted separately and they don't expect its data to be erased. So for any app that saves on the phone, "add it to your Home Screen" is advice that protects people, and it belongs on the app's first screen.

For the Home Screen version to look right the app needs a small settings file called a manifest (its name, its colors, how it opens) and icons in two sizes. Ask for them:

Make it installable
Make this app installable on a phone's Home Screen. Add a web app manifest with a name, a short name, a start address, "standalone" display, and icons at 192 and 512 pixels, plus the icon iPhones use. Keep every link relative, because the site is served from a subfolder. Do not add an offline worker. Then add a short, dismissible note on the first screen that tells iPhone users to tap Share, then Add to Home Screen, and says why. Finish with the steps for me to check it on an iPhone and on an Android phone.
Straight talk

The prompt says "no offline worker" on purpose. An offline worker (a service worker) keeps a copy of the app on the phone so it opens without signal. It also means people can keep seeing an old version after you publish a new one, unless updates were planned for. Add one when someone needs the app with no signal, and ask Claude how updates will reach people before you do. Book 7 has the three ways and how to pick.

Give it a backup

An app with no back end keeps each person's progress in one place: that browser, on that phone. A new phone, a cleared browser or Safari's seven-day rule and it is gone, and nobody can get it back, including you. A backup file is the cheap fix: one button that saves everything to a file, one that loads it again.

Add a backup
Add "Save a backup" and "Restore from backup" to the settings screen. Save writes everything this app keeps in the browser's storage to one dated file the person can keep in their Files app or email to themselves. Restore reads such a file, shows what it holds (the date and how many items) and asks before replacing anything. Refuse a file that isn't one of ours with a plain message. Then give me the steps to prove it works: save on one browser, restore on another, and the same progress shows.

Do the proof yourself, on two browsers or two phones. A backup that has never been restored is a guess.

  • What it costs: nothing to run. The person has to remember to press the button, so show the date of their last backup and nudge them when it is old.
  • What it exposes: the file is readable by anyone who gets it. Fine for flashcard progress. If the app holds anything private, say so beside the button.
  • When it stops being enough: when people want the same progress on two devices, or you need to see their data. That is the moment for a login and a database, which is a bigger step with its own checks (Start here, "What needs a check before launch").
